# Security

The coordinator uses its authenticated GitHub CLI session for policy reads and mutations. Workers receive a small environment allowlist, no GitHub/SSH/cloud credentials, a disabled Git credential helper, and no remote in attempt worktrees. Logs and diagnostics pass through credential-shape redaction; release validation scans every regular candidate file, including ignored `.env` files and the validator itself, for common GitHub token and private-key forms without printing matching contents or paths. It prunes only Git metadata/worktrees and generated `dist` output; Git history, logs, tmux, and published artifacts remain explicit external scans.

## Two boundary modes, two different guarantees

By default (no `install-host` run), the implementation/review boundary runs under the same OS process identity as the coordinator — there is no separate `agent-symphony-worker`/`agent-symphony-reviewer` account. This zero-admin default **defends against accidental credential leakage**: the agent's environment is explicitly filtered, attempt worktrees get no Git credential helper or remote, and the git/tmux command surface the coordinator relays stays allowlisted and confined under a private (mode `0700`) local root. It does **not** defend against a malicious or compromised coding agent: because the agent runs as the same OS user as the coordinator, an agent that deliberately goes looking has the same filesystem and process access as the coordinator itself, including GitHub CLI and SSH/cloud credential storage.

The advanced host-isolated mode (`install-host --coordinator USER`) closes that gap with real OS-enforced separation: the worker and reviewer run under fixed, unprivileged, no-login `agent-symphony-worker`/`agent-symphony-reviewer` accounts that cannot open the coordinator's files at all, regardless of what the agent process tries. Choose it whenever the threat model includes a malicious or compromised agent, not just accidental leakage.

Before a pilot, verify the worker identity boundary, filesystem permissions, tmux history, retained logs, config, Git history, and release artifacts contain no credential. A clean pattern scan is supporting evidence, not proof that an unknown secret format was absent. Rotate any credential suspected of exposure and preserve only redacted incident evidence.

`install-host` must run as root from the root-owned versioned release path. It writes only the exact no-argument implementation, review, and optional-orchestrator `agent-host` sudo tuples. `agent-host` rechecks its effective user and primary group in advanced mode; in the zero-admin default it instead runs as a plain subprocess of the coordinator, with no separate identity to verify. The implementation/review adapters accept one bounded JSON value and permit only Git/tmux execution below their provisioned roots. The orchestrator adapter reads one bounded, non-writable launch contract below the reviewer root. Every path re-applies the shared credential environment filter and grants no GitHub authority.

Fresh GitHub permission checks authorize actors. `agent-ready` authorizes dispatch only when it follows the latest body edit; `autonomous-merge` is a separate opt-in that must satisfy the same boundary. Without `autonomous-merge`, the coordinator never submits a merge. Required checks, commit statuses, review state, current head, and any available branch protection are re-read before an autonomous merge; the coordinator never uses an administrative bypass.

## Local dashboard boundary

The per-repository dashboard binds only to localhost or a loopback IP by default. `--allow-unsafe-dashboard-network` explicitly permits another listen address only when a nonempty `--dashboard-password` is also supplied. Every route then requires HTTP Basic authentication with the fixed username `agent-symphony`; the same password can optionally protect loopback mode. The comparison is constant-time, but there is no rate limiter and direct HTTP does not encrypt credentials or terminal traffic. The password value can also be visible in process listings. Treat this as trusted-network convenience, restrict the port with the host firewall, and use an encrypted VPN or tunnel for untrusted networks.

Static Next.js assets are embedded in the Go binary, `status.json` and `dashboard-state.json` are bounded non-symlink files, and the browser receives no GitHub credentials or feedback bodies.

Terminal, cleanup, and recovery requests require the dashboard origin and re-resolve issue/attempt numbers against the current bounded projection. The browser cannot name a repository, tmux session, worktree, branch, path, marker, prompt, or command. Terminal input and resize messages are size-bounded. Archive accepts only an exact completed attempt and preserves its diagnostic manifest/log; Abandon accepts only an exact orphaned attempt and deletes its local record only after boundary cleanup succeeds. Recover accepts only a server-marked retryable attempt, rereads GitHub and local identity under the reconciliation lock, preserves diagnostic resources, and records the fixed retry control only after the authenticated coordinator's current maintain/admin permission is verified. The server rejects ambiguous attempts, state changes, projected/local identity drift, unsafe files, and non-loopback listening without the explicit password-protected opt-in.

The optional orchestrator agent is advisory. It receives no raw issue body, review text, chat transcript, or GitHub authority. In advanced mode, one exact sudo rule permits only `agent-host orchestrator` as the reviewer identity; the coordinator still owns the attachable tmux session. The launch workspace is setgid to the reviewer snapshot group, and the host accepts the mode-`0440` launch contract only when its actual group matches that boundary. The contract carries only the validated command and sanitized context. Zero-admin mode retains the documented same-user limitation, so use a read-only agent sandbox and keep the dashboard on loopback.
