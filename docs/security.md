# Security

The coordinator uses its authenticated GitHub CLI session for policy reads and mutations. Workers receive a small environment allowlist, no GitHub/SSH/cloud credentials, a disabled Git credential helper, and no remote in attempt worktrees. Logs and diagnostics pass through credential-shape redaction; release validation scans every regular candidate file, including ignored `.env` files and the validator itself, for common GitHub token and private-key forms without printing matching contents or paths. It prunes only Git metadata/worktrees and generated `dist` output; Git history, logs, tmux, and published artifacts remain explicit external scans.

## Two boundary modes, two different guarantees

By default (no `install-host` run), the implementation/review boundary runs under the same OS process identity as the coordinator — there is no separate `agent-symphony-worker`/`agent-symphony-reviewer` account. The default Codex implementation and reviewer commands also disable their sandboxes and approval prompts. Environment filtering and credential-free worktrees still reduce accidental credential use, but they do not constrain a malicious or compromised coding agent: both roles have the coordinator user's filesystem and process access, including GitHub CLI and SSH/cloud credential storage.

The advanced host-isolated mode (`install-host --coordinator USER`) closes that gap with real OS-enforced separation: the worker and reviewer run under fixed, unprivileged, no-login `agent-symphony-worker`/`agent-symphony-reviewer` accounts that cannot open the coordinator's files at all, regardless of what the agent process tries. Codex full access then applies only inside the worker account's OS permissions. Choose this mode whenever the threat model includes a malicious or compromised agent, not just accidental leakage.

Before a pilot, verify the worker identity boundary, filesystem permissions, tmux history, retained logs, config, Git history, and release artifacts contain no credential. A clean pattern scan is supporting evidence, not proof that an unknown secret format was absent. Rotate any credential suspected of exposure and preserve only redacted incident evidence.

`install-host` must run as root from the root-owned versioned release path. It writes only the exact no-argument implementation, review, and optional-orchestrator `agent-host` sudo tuples. `agent-host` rechecks its effective user and primary group in advanced mode; in the zero-admin default it instead runs as a plain subprocess of the coordinator, with no separate identity to verify. The implementation/review adapters accept one bounded JSON value and permit only Git/tmux execution below their provisioned roots. The orchestrator adapter reads one bounded, non-writable launch contract below its snapshot root. Every path reapplies the shared credential environment filter.

Fresh GitHub permission checks authorize actors. `agent-ready` authorizes dispatch only when it follows the latest body edit; `autonomous-merge` is a separate opt-in that must satisfy the same boundary. Without `autonomous-merge`, the coordinator never submits a merge. Required checks, commit statuses, review state, current head, and any available branch protection are re-read before an autonomous merge; the coordinator never uses an administrative bypass.

## Local dashboard boundary

The per-repository dashboard binds only to localhost or a loopback IP by default. `--allow-unsafe-dashboard-network` explicitly permits another listen address only when `--dashboard-password-file` names a coordinator-owned regular file with no group or other permissions. The coordinator reads the one-line password from that file, so the credential is not exposed in process arguments. Every route then requires HTTP Basic authentication with the fixed username `agent-symphony`; the same password file can optionally protect loopback mode. The comparison is constant-time, but there is no rate limiter and direct HTTP does not encrypt credentials or terminal traffic. Treat this as trusted-network convenience, restrict the port with the host firewall, and use an encrypted VPN or tunnel for untrusted networks.

Worker-message actions additionally require a signed browser session. The server issues its HttpOnly, SameSite cookie only during an authenticated document navigation; Basic-authenticated HTTP clients without that browser session cannot submit a direct follow-up or confirm or cancel a proposal. Proposal confirmation also requires a nonce bound to the exact reviewed proposal. These checks prevent accidental conversational delivery; they are not an OS security boundary against a same-user full-access orchestrator.

Static Next.js assets are embedded in the Go binary, `status.json` and `dashboard-state.json` are bounded non-symlink files, and the browser receives no GitHub credentials or feedback bodies.

Terminal, cleanup, recovery, and worker-follow-up requests require the dashboard origin and re-resolve issue/attempt numbers against the current bounded projection. Fixed implementation and reviewer terminal routes accept only issue and attempt numbers; the server derives and compares the role's deterministic tmux name. Unknown roles and projected name drift fail closed. Reviewer attachment uses tmux read-only mode and rejects terminal input. The browser cannot name a repository, tmux session, worktree, branch, path, marker, prompt, or command. Terminal input and resize messages are size-bounded. A follow-up body is bounded to 8192 bytes and reaches GitHub only for the authenticated exact projection with one verified deterministic local owner. This durable queue write grants no worker authority: target-only delivery freshly verifies GitHub controls, attempt binding, terminal state, base/head identity, and runtime ownership before and at worker acceptance. Archive accepts only an exact completed attempt and preserves its diagnostic manifest/log; Abandon accepts only an exact orphaned attempt and deletes its local record only after boundary cleanup succeeds. Recover accepts only a server-marked retryable attempt, rereads GitHub and local identity under the reconciliation lock, preserves diagnostic resources, and records the fixed retry control only after the authenticated coordinator's current maintain/admin permission is verified. The server rejects ambiguous attempts, state changes, projected/local identity drift, unsafe files, and non-loopback listening without the explicit password-protected opt-in.

The optional orchestrator agent is advisory and receives bounded sanitized projection updates rather than raw issue bodies, review text, or chat transcripts. In zero-admin mode it runs as the coordinator user. Configuring Codex with `danger-full-access` lets it use that user's GitHub CLI login and tmux server, but also removes filesystem and process isolation from the model; prompt instructions are the only read-only limit on those tools. In advanced mode, one exact sudo rule launches `agent-host orchestrator` as the reviewer identity, whose home, credential stores, and tmux server are separate from the coordinator and worker identities. The fixed proposal helper validates one bounded JSON object and writes a pre-created regular file with mode `0620` while holding an exclusive file lock. The coordinator uses a shared lock when reading it and records only binding digests and bounded outcomes in the mode-`0440` status file; the fixed status helper has no coordinator mutation operation.
