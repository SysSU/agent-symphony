# Recovery

GitHub markers and current issue/PR state are authoritative; local manifests are bounded diagnostic state. On startup the coordinator acquires its runtime-state lock, reads authoritative attempts, checks exact deterministic worktree/session/head identities, reconciles terminal work, and only then schedules eligible issues. Separate repository daemons use separate state roots; shared resource names include the repository identity so one daemon cannot discover or clean another's resources.

Before local launch, dispatch writes a strict coordinator-authored active-attempt comment binding the issue, attempt, deterministic branch, and approved base. Restarts and repeated polls resume that binding through implementation, review, and publication while current issue controls remain authorized; revoked controls cancel a live worker and suppress publication. Final PR or terminal markers supersede the binding, so a restart cannot create a duplicate attempt or PR. Foreign, conflicting, or unverifiable bindings and contradictory authoritative PR attempts block mutation.

A terminal failure is authoritative only when it pairs with the coordinator-authored active marker for the same issue and attempt. The dashboard retains every trusted paired failure in the attempt history instead of calling earlier failures orphaned; only the latest uncontested failure can authorize a retry. For an unpublished live attempt, the checked-out head may equal or descend from the approved base; a published attempt must still match GitHub's exact head.

**Recover attempt** is available only for the latest unblocked paired failure or an active attempt whose exact local branch, head, or tmux liveness check failed. After confirmation, Agent Symphony rereads GitHub and the deterministic local manifest under the reconciliation lock. A stuck live attempt is stopped and marked failed before the dashboard records the exact `/agent-symphony retry` control. Existing worktrees, manifests, and logs are preserved. Missing, unsafe, or noncanonical worktrees require manual repair and never trigger cancellation or GitHub mutation. Marker conflicts, changed identities, published pull requests, and stale or ambiguous requests are refused.

For an orphaned attempt, first compare GitHub markers with the retained manifest, branch, worktree, and named tmux session, then use `status`, `inspect`, and `reconcile`. If the work was completed by a different authoritative attempt and this exact local attempt is no longer useful, the dashboard's confirmed **Abandon attempt** action stops only its deterministic session, removes only its deterministic worktree/result and retained manifest/log, and hides the stale card. Never delete, attach to, or adopt an unidentified resource to make recovery proceed.

For a completed attempt, the dashboard's confirmed **Archive** action re-runs the same strict cleanup used by reconciliation: the implementation boundary verifies the deterministic branch and reviewed head, stops only the exact tmux session if it remains, and removes the local clone (including its local branch) and worker result. The recovery manifest and log remain as diagnostics; `dashboard-state.json` only records that the completed card is hidden and never changes GitHub workflow truth.
