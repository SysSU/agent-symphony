# Recovery

Coordinator comments contain machine-readable **markers** that identify attempts. Those markers and current issue/PR state are authoritative. A local **manifest** is a small JSON record used only to find and diagnose runtime resources. On startup the coordinator locks its runtime-state directory, reads authoritative attempts, checks exact worktree/session/head identities, reconciles terminal work, and only then schedules eligible issues. Separate repository daemons use separate state roots; shared resource names include the repository identity so one daemon cannot discover or clean another's resources.

For state meanings and operator next steps, see [Status and next actions](cli.md#status-and-next-actions).

Before local launch, dispatch writes a strict coordinator-authored active-attempt comment binding the issue, attempt, deterministic branch, approved base, worktree, and tmux session. The daemon passes that identity directly to the implementation session; the optional advisory orchestrator is not part of dispatch. Restarts and repeated polls resume that binding through implementation, review, and publication while current issue controls remain authorized; revoked controls cancel a live worker and suppress publication. Publication prepares the exact head transition locally before push. An idle stale record can also advance from an exact coordinator-owned PR marker plus its matching coordinator-authored issue marker; unconfirmed heads and records with in-flight work remain blocked. Final PR or terminal markers supersede the binding, so a restart cannot create a duplicate attempt or PR. Foreign, conflicting, or unverifiable bindings and contradictory authoritative PR attempts block mutation.

A terminal failure is authoritative only when the coordinator also recorded the active marker for the same issue and attempt. This is a **paired failure**. The dashboard keeps every paired failure in attempt history instead of calling earlier failures orphaned; only the latest uncontested failure can authorize a retry. For an unpublished live attempt, the checked-out head may equal or descend from the approved base. A published attempt must still match GitHub's exact head.

**Recover attempt** is available only for the latest unblocked paired failure or an active attempt whose exact local branch, head, or tmux liveness check failed. After confirmation, Agent Symphony rereads GitHub and the deterministic local manifest under the reconciliation lock. A stuck live attempt is stopped and marked failed before the dashboard records the exact `/agent-symphony retry` control. Existing worktrees, manifests, and logs are preserved. Missing, unsafe, or noncanonical worktrees require manual repair and never trigger cancellation or GitHub mutation. Marker conflicts, changed identities, published pull requests, and stale or ambiguous requests are refused.

For an orphaned attempt, first compare GitHub markers with the retained manifest, branch, worktree, and named tmux session, then use `status`, `inspect`, and `reconcile`. If the work was completed by a different authoritative attempt and this exact local attempt is no longer useful, the dashboard's confirmed **Abandon attempt** action stops only its deterministic session, removes only its deterministic worktree/result and retained manifest/log, and hides the stale card. Never delete, attach to, or adopt an unidentified resource to make recovery proceed.

For a completed attempt, the dashboard's confirmed **Archive** action re-runs the same strict cleanup used by reconciliation: the implementation boundary verifies the deterministic branch and reviewed head, stops only the exact tmux session if it remains, and removes the local clone (including its local branch) and worker result. The recovery manifest and log remain as diagnostics; `dashboard-state.json` only records that the completed card is hidden and never changes GitHub workflow truth.

When `commands.orchestrator` is configured, reconciliation also checks the exact `as-o-<repository-id>` pane. A live pane is adopted with its tmux scrollback. A missing or dead pane becomes a fresh local generation from sanitized current status, including bounded, redacted issue blockers. A changed full projection starts a separate one-shot audit, or remains pending by digest while one is running; unchanged nonterminal work also starts one at most every five minutes. The persisted start time prevents an immediate duplicate after restart. The one-shot process gets the last validated projection, bounded prior completed report, and any reconciliation failure, then inspects the last verified transition, expected next transition, and available live GitHub, tmux, manifest, handoff, result, and log evidence. A workflow or GitHub transition, commit change, meaningful tmux output change, or direct owner reply is progress. A stall is actionable only when two observations at least one heartbeat interval apart show none of those signals. It has a four-minute deadline and its bounded, redacted result atomically replaces `orchestrator-heartbeat-report.json`. The audit output cannot create a handoff or authorize recovery. The auditor may only use the direct GitHub status contract to set a specific needs-attention reason for a verified blocker or actionable stall, skip an identical current update, or clear its own prior reason after fresh recovery evidence.

After the audit ends, the coordinator may derive one exact attention handoff from its own structured `blocked`, `failed`, `conflicting`, `orphaned`, or explicitly needs-attention projection. If no audit command is configured, this structured handoff does not wait for an audit. An authorized active or review-ready attempt with no pull request is also eligible when its implementation session is complete but its phase remains validation or publication. The coordinator persists the handoff and its deduplication digest before sending one fixed prompt to the primary pane. The prompt names `orchestrator-attention-handoff.json`, preserves authorized human-instruction precedence, and permits only the fixed `check_in_attempt`, `retry_transition`, `recover_attempt`, or a non-mutating `human_attention` result. A check-in is accepted only for an exact active needs-attention attempt with one verified live implementation owner. It sends a fixed progress request through the existing worker boundary, includes no arbitrary message or implementation direction, and waits for fresh direct status evidence. The primary must re-check live evidence and poll any proposal to a terminal outcome. The coordinator then reads a fresh projection. It records `recovered` only when that projection no longer requires attention for the exact target; otherwise it records `human-attention`. An unchanged target cannot wake again. A materially changed target may create one new handoff. A restart does not repeat a delivered or ambiguous wake.

After a coordinator restart, an unfinished `running` audit report becomes a local failed lifecycle record instead of remaining stale. Issue text and audit prose remain untrusted data, and only fixed Agent Symphony controls may mutate workflow state. If GitHub is unavailable after a restart, recovery reuses the validated durable context instead of replacing it with an empty projection; without durable context it defers recreation. Removing `commands.orchestrator` stops only the deterministic pane and persists the disabled state. Failed launches persist a redacted diagnostic and exponential retry time rather than relaunching each poll. Clear, rebuild, and audit remain local advisory state and cannot override issue, attempt, pull-request, or merge facts.

The service observes the fixed, protected orchestrator proposal artifact independently of dashboard polling. A `retry_transition` proposal needs no second approval because it can only invoke one guarded reconciliation for a freshly verified, unblocked active attempt with a completed implementation result awaiting validation or publication. A `recover_attempt` proposal must match the current attention handoff and reuses the dashboard's guarded recovery path for the exact latest retryable failure or exact runtime-liveness mismatch. It cannot recover a target with a pull request, unsafe or mismatched local identity, ambiguity, or revoked retry authority. `human_attention` records a bounded reason and makes no GitHub or runtime mutation. Durable status records `pending`, `running`, and one terminal `succeeded`, `failed`, or `refused` outcome. Completed-result processing runs before global pull-request governance, fixed actions have a ten-minute deadline, and errors retain the failing stage. These controls add no arbitrary worker message, restart, cancel, abandon, check-rerun, merge, tmux, shell, or general GitHub mutation authority.
